# Hacker News Monitor

Мониторинг упоминаний и отношения к выбранной сущности в комментариях Hacker News.
Дашборд предназначен только для просмотра: упоминания, настроение, источники и комментарии.
Запрос мониторинга и параметры обработки задаются в YAML; техническое управление доступно через API и CLI.
В проекте **шесть микросервисов**: пять основных и отдельный Teacher для автоматической разметки.

## Быстрый запуск всех шести сервисов

Нужны работающий Docker с Compose и Python 3. Команды выполняются из корня проекта.
Python на компьютере запускает только демонстрационный клиент; зависимости сервисов устанавливаются в образы.

```sh
# Необязательно: создать файл настроек, сохранив существующий .env.
cp -n .env.example .env
python3 demo/start.py --dataset 1k --with-teacher
```

Команда собирает **шесть контейнеров**, ждёт готовности, прогоняет E2E и оставляет систему работающей.
E2E импортирует 1000 комментариев, обучает небольшой классификатор и сохраняет его оценки.
Teacher запущен, но его нейросеть не загружается: демо использует уже размеченный датасет.
Первой сборке нужен интернет для зависимостей; Swagger загружает стандартный интерфейс с CDN.

| Что открыть | Адрес |
|---|---|
| Дашборд | [localhost:8080](http://127.0.0.1:8080/) |
| Единый Swagger, разделы всех шести сервисов | [localhost:8080/gateway-docs](http://127.0.0.1:8080/gateway-docs) |
| API Web Master | [localhost:8081/docs](http://127.0.0.1:8081/docs) |
| Прямой Swagger Teacher | [localhost:8082/docs](http://127.0.0.1:8082/docs) |

| Роль | Логин | Пароль | Возможности |
|---|---|---|---|
| Администратор | `admin` | `admin-demo` | Дашборд и технические операции через API/CLI |
| Читатель | `viewer` | `viewer-demo` | Чтение моделей, графиков, комментариев и отчётов |

В Swagger нажмите **Authorize** и введите учётные данные. Порты доступны только с этого компьютера.
Порты и пароли задаются в `.env` или переменных `MONITOR_*` из [.env.example](.env.example).
Скрипт запуска учитывает эти же порты и пароли при проверке E2E.

## Полная выгрузка и остановка

Для 10 000 комментариев остановите меньшую версию: стандартные порты у них общие.

```sh
docker compose -p hn-monitor-demo-1k down
python3 demo/start.py --dataset 10k --with-teacher
```

Версии используют отдельные проекты и тома: `hn-monitor-demo-1k` и `hn-monitor-demo-10k`.
Чтобы остановить полную версию: `docker compose -p hn-monitor-demo-10k down`.
Обычный `down` сохраняет данные и модели. Для параллельного запуска задайте разные `MONITOR_UI_PORT`, `MONITOR_API_PORT`, `MONITOR_TEACHER_PORT`.

Без `--with-teacher` запускаются **пять основных сервисов**. Это облегчённый режим для готовой разметки;
шестой сервис подключается профилем Compose `training`, когда нужен его API или новая разметка.
Подробности и повторный запуск проверки: [demo/README.md](demo/README.md).

## Четыре пользовательских сценария

После запуска данные уже подготовлены. В интерфейсе нет управления моделями, загрузками или сервисами.

| Сценарий | Действия в дашборде |
|---|---|
| 1. Оценить отношение к теме | Посмотреть число упоминаний, средний балл и динамику за дни или недели |
| 2. Разобрать изменение настроения | Нажать на точку графика и прочитать комментарии выбранного периода; **Все периоды** сбрасывает выделение |
| 3. Найти конкретное обсуждение | Ввести слово или фразу и нажать **Найти**; поиск учитывает выбранный период |
| 4. Сравнить источники и сохранить результат | Посмотреть таблицу источников и нажать **Скачать отчёт** |

Тема берётся из `monitoring.query`. Модель задаётся `pipeline.model_id`; если ID не указан,
используется последняя обученная модель выбранного `pipeline.model_kind` для этой темы.
Дашборд обновляется автоматически; период и частота обновления задаются в конфиге Visualization.

Разработчик управляет конвейером через Swagger или CLI. Создание и обучение находятся в
`/services/ml/models`, `/services/ml/models/{id}/train`, состояние — `/services/ml/jobs/{id}`.
`POST /api/score` принимает `model_id`, `entity`, `limit`, применяет закреплённую версию и сохраняет оценки.
Новый текст можно проверить через `/services/ml/models/{id}/predict`. Эти операции не выполняются из дашборда.

## Архитектура и API

Каждый сервис имеет собственные `main.py`, `config.yaml`, `Dockerfile`, зависимости и HTTP API.
Внутри Docker все слушают порт 8000; наружу опубликованы только три адреса ниже.

| Сервис | Ответственность | Адрес в Docker | Порт компьютера |
|---|---|---|---|
| Collector | Источники, батчи, журнал загрузок | `collector:8000` | — |
| Storage | SQLite, поиск FTS5, CRUD комментариев, оценки и разметка | `storage:8000` | — |
| ML | Создание, обучение, валидация, предсказания, версии и задачи | `ml:8000` | — |
| Web Master | Авторизация, маршрутизация, импорт, оценка, аналитика, отчёт | `web_master:8000` | 8081 |
| Visualization | Plotly Dash и общий Swagger | `visualization:8000` | 8080 |
| Teacher | Автоматическая разметка через отдельную модель | `teacher:8000` | 8082 |

Контракты моделей находятся **только в разделе ML**. Web Master пересылает их через общий
`/services/{service}/…`; повторных `/api/models` и `/api/jobs` нет.
Собственный API Web Master содержит семь операций:

- `GET /api/config` — запрос мониторинга, источники, шкала и текущая роль;
- `GET /api/status` — состояние сервисов и последние загрузки;
- `POST /api/import` — получить и сохранить батч;
- `POST /api/score` — оценить сохранённые комментарии;
- `GET /api/comments` — комментарии, поиск и даты; `model_id` добавляет оценки;
- `GET /api/analytics` — сводка, временные периоды и источники;
- `GET /api/report` — HTML-отчёт.

Через gateway баллы и MAE пересчитываются в настроенную шкалу; вероятности классов остаются исходными.
Внутренний ML использует шкалу 0–5. Storage агрегирует сохранённые данные по ключу `id:version`,
а Web Master выбирает версию модели, правила упоминаний и шкалу для пользовательского результата.

## Датасеты и модель

[demo/hn_10k.json](demo/hn_10k.json) — 10 000 настоящих комментариев из 60 тредов;
[demo/hn_1k.json](demo/hn_1k.json) — детерминированное подмножество на 1000 строк.
Сохранены ссылки, даты, заголовки и контекст ответов. Происхождение и SHA-256:
[10k](demo/hn_10k.metadata.json), [1k](demo/hn_1k.metadata.json).

Каждая строка содержит `label`, `label_entity`, `label_source`, `label_fingerprint`.
Загрузчик сверяет метку с сущностью и отпечатком контекста. Классы A–E означают
тональность от отрицательной до положительной, F — отсутствие отношения к сущности.
На шкале 0–5 классы A–E соответствуют 0; 1,25; 2,5; 3,75; 5. У F нет балла.

По умолчанию обучается `hard_label`: TF-IDF слов и символов плюс линейный классификатор.
Также доступны `softmax` и `tiny_mlp`. Этим режимам не нужны GPU или веса трансформеров.
Метрики проверки модели доступны в техническом API и показывают согласие с подготовленными метками: около 70% не означает независимую
человеческую точность. Разметка объединяет проверку ассистентом, правила и заранее вычисленные
модельные оценки. Это целевая выборка, а не перепись всей аудитории HN.

`from_scratch` обучает новую версию; `incremental` использует новые/изменённые примеры
и часть прежних. Без новых меток возвращается `skipped`. Треды обучения и проверки разделены,
артефакты версий хранятся в SQLite с проверкой SHA-256.

## YAML-конфигурация и новые данные

В [config.yaml](config.yaml) задаются запрос, алиасы, правила и источник:

```yaml
monitoring:
  query: ChatGPT
  aliases: [Chat GPT]
  source: hacker_news
  matching: {allow_typos: true, allow_context: true, context_hints: []}
offline_demo: true
path_to_offline_demo_data: demo/hn_1k.json
pipeline:
  model_id: null
  model_kind: hard_label
  teacher: dataset
  training_limit: 10000
```

`offline_demo: false` включает живой сбор. Учтены прямое имя, алиасы, небольшие опечатки
и простые отсылки в ближайшем контексте. Новый источник наследуется от `NewsProvider` и возвращает
общие `News`/`NewsComment`: [пример расширения](runtime/collector/README.md).
Для собственной выгрузки есть `python3 runtime/collector/fetch_snapshot.py`.
Для обучения новых текстов нужны соответствующие метки: `dataset`, `reviewed`, `service` или `live`.

В [конфиге Web Master](runtime/web_master/config.yaml) `score_scale: {min: 0, max: 10}` меняет шкалу GUI, отчёта и gateway.
В [конфиге Teacher](runtime/teacher/config.yaml) находятся веса автоматического разметчика;
в [конфиге ML](runtime/ml/config.yaml) — параметры малого классификатора, опционального NLI-энкодера и llama.cpp.
Формат весов общий, имя модели не зашито в код:

```yaml
model_weights:
  path: https://huggingface.co/owner/model/resolve/revision/model.onnx
  is_local: false
```

Для локального файла задайте его путь и `is_local: true`, согласовав SHA-256, токенизатор и формат модели.
`teacher: service` обращается к шестому сервису; веса скачиваются только при реальной разметке.
`kind: semantic` отдельно включает NLI-энкодер. GGUF-режим `teacher: live` использует `model_weights`,
параметры `llama_*` и Docker-target `with-llama` через `ML_IMAGE_TARGET=with-llama`.
Эти режимы требуют дополнительных ресурсов; обычное демо их не запускает. [Подробнее о Teacher](runtime/teacher/README.md).

## Проверки, нативный запуск и структура

```sh
# На уже работающем демо; размер должен совпадать с запущенным.
python3 demo/e2e.py --dataset 1k --compare
```

CI запускает этот E2E для 1k и 10k с пятью основными контейнерами, проверяет оба малых классификатора,
импорт, права, обучение, оценки, отчёт и отсутствие скачанных ONNX/GGUF-весов. Teacher для готовых меток не нужен.
При своих паролях экспортируйте их для отдельного CLI, при другом порте передайте `--url`.

Нативный вариант: Python 3.12, виртуальное окружение, `pip install -r requirements.txt`,
затем `python demo/run.py --dataset 1k --with-teacher`. Web Master будет на 8103, GUI — 8104, Teacher — 8105;
E2E запускается в другом терминале с `--url http://127.0.0.1:8103`.
Ежедневное обновление: `python runtime/web_master/daily.py --model-id <id>`; для новых данных подготовьте метки или подключите Teacher.

- `lib/` — общие контракты, конфигурация, HTTP-клиент, упоминания и веса;
- `runtime/` — шесть микросервисов;
- `demo/` — два размеченных датасета и запуск/E2E;
- `.github/workflows/ci.yml` — автоматическая проверка;
- [grade.md](grade.md) — соответствие каждому пункту задания и ожидаемые баллы.

Данные и модели работающей системы живут в Docker-томах или `.local-data/` при нативном запуске.
Логи прогонов, выгруженные отчёты и скачанные веса в репозиторий не добавляются.
